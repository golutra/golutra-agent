## 已有能力应保留

Golutra 已实现单层委派、可配置并发额度（默认 10）、原子入场、共享预算和恢复检查点。子会话的归属、工作区和父子关系受校验；取消有回收流程，host 关闭会结束受管子任务。

`subagent` 已提供 `spawn/status/wait/send_input/resume/cancel`。`resume` 复用原子会话，新的执行用 task 身份区分；重复派发有去重，等待结果绑定具体执行。等待超时不会取消子任务，已完成结果可以重复读取和分页。

上下文支持 independent 与显式 fork。fork 冻结父请求快照并校验来源、哈希、大小、消息配对及模型兼容性。`explore` 有工具和运行时写入限制，不只是提示词。worktree 明确从 HEAD 建立，不包含父工作区的未提交改动，这一行为已有合同和测试。

`SubagentUpdated` 已持久化、去重并能重建；活跃模型循环会读取，后续用户轮次也有历史投影。不能把下面的自动唤醒缺口描述成“所有子代理结果都会丢失”。

主要依据：`crates/golutra-agent-client/src/delegation{,_policy,_context,_control,_worktree,_notifications}.rs`，以及 `crates/golutra-agent-runtime/src/subagent_parallel_tests.rs`。

## 优先处理的缺口

| 优先级 | 当前行为与触发条件 | 影响与建议 |
| --- | --- | --- |
| P1 | general 子代理继承 Full 工具集时仍可调用 `ask_user`，子会话等待自己的回答通道；父委派等待器没有问题转交，TUI 只订阅当前父 session/task | 用户看不到子问题，父代理等待可能持续到取消或外部时间预算触发。先关闭不可交互子代理的问题入口或返回结构化 `needs_input`；之后由父代理承接、处理或转交真正必要的问题 |
| P1 | 后台子代理完成写入 `SubagentUpdated`，通用后台任务结束等待却只检查 BackgroundToolSupervisor | 父轮次已经收尾时，子结果不会按“本批全部完成后再汇总”的规则继续父代理。接入统一交付及唤醒协调，保留子代理自身执行器 |
| P2 | 子代理 `wait` 仅等待结果、超时或取消；运行时在工具批次结束后才取新 steer | 用户补充指令不能及时结束这次等待。将用户输入活动加入等待条件；只结束等待，不取消子代理 |
| P2 | `send_input` 仅支持活跃子代理；空闲子代理需另调 `resume`，没有独立的只入队消息模式 | 状态检查与发送之间可能发生结束竞争，调用方需要自己重试或改操作。内部统一消息投递，明确 `queue_only` 与 `continue`，延续原子会话身份 |
| P2 | 汇总状态最多列 16 个子会话，没有分页游标；通知索引持全局缓存锁跨数据库读取 | 长会话的发现和查询成本会扩大。增加可分页注册表/状态投影、按 session 更新和有界缓存；先量测再定性能目标 |

### P1：提问与审批

调用链为：`execution.rs:1482` 仅从子工具集中移除 `subagent` → `delegation.rs:1324` 继承父工具配置 → `runtime/src/lib.rs:3102` 等待 `ask_user` 回答 → `lib.rs:5124` 只监听回答和取消。

父侧 `delegation.rs:1408` 的 `wait_for_child` 处理终态、审批、认证和取消，没有子问题转交分支；`tui/src/runtime_controller.rs:421` 的订阅限定当前 session/task。此问题取决于 Full 工具集等前提，不能说所有默认 Coding 子任务都会挂起。

现有审批会直接拒绝，认证等待会取消，这是明确的保守策略，不是权限绕过。但交互 TUI 缺少父会话承接子代理请求的路径。Codex 官方文档明确支持呈现非当前子线程的审批并跳转来源；值得借鉴其路由方式，不应直接复制宽松权限。

建议问题携带稳定的 child/session/task/question 身份。父代理能回答的内部问题先内部处理；需要用户决定时由父会话合并呈现。无交互运行应给出明确 blocked 原因，不能不可见地无限等。用户取消或子任务换代后，迟到的回答不得应用到新执行。

### P1：后台结果交付与唤醒

`runtime/src/lib.rs:2599` 在模型收尾前再次取子代理通知，但随后的 `background.rs:326` 只订阅通用后台活动，并用 `has_pending_background_tasks(session, turn)` 决定是否等待。`tools/src/lib.rs:3356` 的子代理派发没有登记到该 supervisor。

因此正常边界可以收结果，父轮次已结束后的自动汇总仍有缺口。Codex V2 在 `core/src/agent/control/completion.rs:116` 将完成结果按 `trigger_turn=false` 入队；`multi_agents_v2/wait.rs:69` 订阅消息和输入活动。不能把 Codex 描述为“每个完成通知都会主动启动一轮”。

适合本项目的策略延续用户此前偏好：

1. 结果先持久入队，不逐条通知用户；有新用户输入时，将尚未消费的结果与该输入一起交给父代理。
2. 没有用户输入时，按父轮次封口的任务批次判断完成，全部结束后最多触发一次内部汇总；不能等待全局所有任务。
3. 用户输入和自动汇总同时到达时优先用户输入，并合并结果。已经消费的批次不重复唤醒。
4. 父任务明确取消后保存迟到结果，但不重新启动；失败、需要输入和未知结果保留真实状态，不能作为成功完成。
5. 以稳定 result 身份和投递确认实现重放去重，不宣称分布式意义上的 exactly-once，也不因重放重新执行副作用。

### P2：等待、消息和长期身份

`delegation_control.rs:255` 在没有 `wait_ms` 时等待整个操作完成；显式有界等待先等 ready，再计算等待上限。`bounded_wait` 没有用户输入活动分支。`runtime/src/lib.rs:3630` 在工具批次结束后才获取 steer，外层调用也没有输入抢占，因此这个差异不只是工具接口命名。

Codex V2 的 `wait_agent` 可返回 `Steered`，`AgentControl` 的消息投递区分 `QueueOnly` 和 `TriggerTurn`。其目标解析、冷恢复和空闲 runtime 回收分属独立模块，稳定 agent 身份与当前是否常驻分开。

Golutra 已有稳定 child session 和 execution task 身份，应在此基础上增加可读名字、状态查询与投递模式。保留当前单个 `subagent` 工具也可以；工具数量多少不是架构质量指标。兄弟代理通信若将来增加，仍需明确父子归属和可达范围，不能因支持名字寻址放宽权限。

### P2：长会话成本和产品入口

`delegation_notifications.rs:45` 在持有全局缓存锁时分多页读取。超过 4096 facts 或 2 MiB 的 session 不继续缓存，下次可能重新全量扫描；`reconcile:251` 中还有按每个完成事件线性查找来源事件的过程。这是有源码依据的放大风险，本轮没有测得具体延迟或吞吐降幅。

completed operations 会在父控制清理时移除，不能声称是永久内存泄漏；长期单个父任务内的保留量可以进一步有界化。Codex 的 runtime eviction 是较长期的容量管理参考，当前应先解决通知扫描和身份索引问题，不必立即实现同等复杂的常驻管理器。

TUI 已有子任务结果行，仍缺少统一查看子任务状态、等待原因、结果、取消、续跑和打开子会话的入口。默认显示短名称、任务摘要和状态；完整 ID、工具参数和诊断放在详情，沿用最近 `/connect` 的用户展示原则。

多代理共享工作区仍应明确文件分工；worktree 隔离应展示 base commit 和是否排除了未提交改动。若确有需求再增加显式快照/补丁模式，不自动把用户未提交内容搬入或覆盖到别处。

## 建议的模块演进

| 模块 | 负责什么 | 复用什么 |
| --- | --- | --- |
| AgentRegistry | 稳定身份、可读名字、父子归属、分页发现 | 现有 thread/session 和 durable 事件 |
| ExecutionController | 每轮 task、预算入场、并发、取消、resume、回收 | 现有 DelegationOperation/DelegationContext |
| Delivery / Inbox | 消息与结果入队、问题转交、投递确认、去重、续跑模式 | 扩展现有 BackgroundInbox 和持久结果存储；子完成通知转换为同一结果的事件投影 |
| WakeCoordinator | 用户输入优先、批次封口、全部结束后继续、取消后禁止重启 | 从现有 HostedBackgroundObserver、pending-turn 和 wake claim 中抽取公共逻辑 |

这是同一运行时内的职责拆分，不需要引入新服务或另建一套调度平台。首先统一“谁在什么条件下收到什么结果”，执行器本身继续保留各自特点。

实施顺序：先补提问死等保护、混合后台批次与子结果交付；再补可被输入唤醒的 wait、两种消息模式和跨代理资源协调；最后补分页索引、TUI 入口及长会话压测。各阶段带专项回归，角色配置、更深递归、自动工作区合并按真实需求另行评估。

## 与已有异步并发的整合方案

本节以 [已经实现的后台任务机制](background-tasks.md) 为基础。异步决定调用何时返回、谁持有执行生命周期；并发决定哪些操作可以同时执行；结果投递决定何时让模型继续。这三个职责要分别保留，使用同一套身份、状态和取消契约衔接。

### 直接复用的实现与需要补齐的接入点

| 已有实现 | 继续复用 | 子代理接入需要补齐 |
| --- | --- | --- |
| core 的 BackgroundScope、Batch、Result 与 WakeClaim | workspace/session/task/turn、批次代次、稳定结果身份 | 记录父派发身份与 child session/task 的关联，区分工具结果、子执行结果和交互请求 |
| store 的批次、结果收件箱、wake claim、交付确认 | 持久化先于可见回执；批次封口；上下文快照落盘后才确认消费 | 子执行完成与父结果入队具备可恢复的提交边界，旧 SubagentUpdated 不再形成第二次模型投递 |
| HostedBackgroundObserver | 所有权 lease、静默投递、原任务有效性检查和唤醒去重 | 将批次协调从工具专属 observer 中抽出，供同一父轮次的 shell、浏览器与子代理共同登记 |
| runtime 的 BackgroundInbox、PendingTurnQueue | 用户输入优先，Passive 与 ContinueAfterBatch，暂停/取消保护 | 待完成检查与活动订阅覆盖子执行，wait 订阅用户输入；全部就绪后沿用当前模型循环 |
| BackgroundToolSupervisor / ProcessSupervisor / 浏览器执行器 | 工具名额、进程回收、浏览器串行和真实结果/图片 | 子代理通过适配层登记生命周期，不包成长期占用工具名额的后台工具 |
| DelegationContext / DelegationOperation | 子代理预算、并发入场、会话恢复、取消和结果读取 | 以具体 execution 完成情况通知公共批次协调，不重建第二套子代理执行器 |

源码确认现有 BackgroundResult 的载荷是 ToolResultEnvelope，observer 也绑定具体 HostedAgentTask。因此接入不能只把 `subagent` 加进后台工具白名单。应通过显式适配记录来源身份、终态、证据引用和投递去重键；现有字段可表达时先复用，确需修改公开 schema 或存储时增加版本化变更和独立迁移，不修改历史迁移 checksum。

### 批次与父子边界

同一父轮次可以启动后台测试、浏览器操作和两个子代理。这些直接启动的操作属于该轮次当前开放的同一批次，封口后不再增加成员。用户新输入时优先消费已有结果；无新输入且本批符合续跑条件时，沿用当前 task/预算/权限继续一次。若继续后又派发任务，建立下一批，不能复用已经封口的成员集合。

子代理内部又启动的 shell、浏览器等后台工具归子代理自己的批次，先交给子代理处理。父批次等待对应 child execution 的结果，不直接接收孙级工具输出。这样可避免重复汇总、越过会话边界、重复统计 token/工具验证以及把内部启动回执当作完成证据。父批次已经包含 child execution，就不再把它的内部工具作为独立成员重复登记。

常规等待采用现有事件驱动方式：保留当前 Agent loop，不做模型轮询，不为每个结果创建新 session/task。只有真正获得下一轮输入或本批续跑资格时才继续推理。若循环已因取消、被替代或退出而关闭，结果保留到允许的后续输入，不靠完成回调偷偷重启。进程退出后的恢复遵循现有 lease 与未知结果规则。

`waiting_for_user`、暂停、取消和 `outcome_unknown` 继续抑制自动续跑。子代理提问先成为带来源的交互事实；交互请求可结束父侧工具等待并返回阻塞原因，避免内部依赖被“等所有结果”挡住。父代理仍活跃时可处理内部问题，真正需要人的问题随下一次用户交互呈现；无交互执行明确返回阻塞状态。需要输入不等同于仍在计算，不能让父侧永远等待“全部成功”。不新增逐个任务的主动用户通知。

### 并发与资源约束

- 保留当前两个额度：子代理默认 10 个，后台工具最多 16 个并发执行。前者限制 Agent 执行，后者限制工具执行；不能简单相加成 26 个同类工作单元，也不能合为一个由父子争抢的信号量。
- 父代理等待子代理时不占 shell/浏览器执行名额；子代理仅在实际调用工具时申请相应资源。先排专用资源、再申请通用执行名额，避免一批等待浏览器的工作堵住 shell。停止后的清理仍持有必要许可直到实际结束。
- 当前浏览器调用在 host 进程内串行，包含前台和后台。父子代理共同遵守这个边界；不同标签页不自动代表可安全并行，任意 Ego 脚本可能影响 Profile、文件或剪贴板。跨 host 的浏览器互斥不能由本机信号量保证。
- 保留已有工具批次分类：安全读取、独立目标的子代理启动/等待、后台进程启动和可解析的不相交路径写入；副作用检查点须在派发前完成，生命周期操作和重叠目标维持屏障。
- 现有路径批次判定不是跨多个 Agent loop 的全局文件锁。跨代理写入先明确文件归属或使用 worktree；公共写入口如增加资源锁，应以一次操作和实际资源键为周期，不能整段子任务持有父工作区锁。任意 shell 的写入范围不能凭名称推断，未知副作用按保守策略协调。
- 保持队列、结果正文、图片和持久未消费结果的上限。容量不足在派发前背压或拒绝，不丢弃未交付证据；预算计费归实际执行，投递与重放不再计成一次执行。

### 接入、迁移与验证顺序

1. 从现有 observer 抽出共享批次协调与结果投递接口，保持 shell/浏览器行为及现有回归不变。先补 Full 子代理不可见提问的保护。
2. 加入 child execution 适配器：派发前持久登记关联，完成后登记结果并发出公共活动信号；runtime 收尾的 pending 判断同时覆盖两类执行。旧 SubagentUpdated 保留为审计/TUI 投影和兼容读取入口，按稳定执行身份去重，不能双重喂给模型。
3. 将子代理 wait、只入队消息与继续执行纳入公共活动机制；实现跨代理资源协调并验证饥饿、取消和身份竞争。
4. 最后做统一后台任务/子任务视图与长会话分页。产品默认展示任务、来源、状态和等待原因，内部调度参数留在详情。

混合验收至少包含：一个父代理同时运行 shell、浏览器和两个子代理，子代理内部再跑后台工具；结果乱序、立即完成、部分失败；用户输入和最后一个结果同时到达；中途取消或暂停；恢复发生在完成记录与交付确认之间；额度耗尽时子工具仍能取得可用资源；两个子代理改同一文件；两个子代理操作浏览器。检查会话/任务身份、执行次数、结果消费次数、验证计数、预算和残留进程，而不只检查最终文字。

补充审查只更新了方案，没有修改实现或重跑上一节的 75 项测试；这些混合场景是后续接入的验收要求，尚不能声称已经通过。

## 验收条件

- Full 子代理提问、headless 无回答、用户取消、迟到回答：没有不可见无限等待，也不扩大授权。
- 父代理已收尾、子结果乱序到达、零任务、快速完成、部分失败、需要输入、重复完成：符合批次规则，无丢失或重复汇总。
- 用户新输入与最后一个结果同时到达、进程重启发生在入队或确认之间：用户输入优先，结果重放可去重，副作用不重执行。
- wait 期间用户 steer：及时结束等待，子任务继续；取消与超时语义保持独立。
- active→idle 竞争、重复 followup、resume 后旧结果到达：身份不变，执行轮次明确，旧结果不覆盖新状态。
- 查询超过 16 个子会话、历史超过缓存阈值、多父会话并发：可完整分页，记录 P50/P95、数据库读取量、队列长度和内存，不能以缩减结果换性能。
- 子任务面板的返回、取消、恢复与跳转不改变会话归属，默认不展示内部提示和原始 JSON。
