# 长程任务与自动纠偏：实现及对照验收

日期：2026-09-19。环境：macOS arm64。Golutra 为 `6b71a74` 之上的本地 0.3.1 源码构建；没有发布 npm。Codex 源码参照 `fc269b66`，实跑二进制为 `codex-cli 0.154.0`，两者不能混称同一构建。

## 本轮实现

| 环节 | 调整前 | 当前行为 | Codex 源码依据 |
| --- | --- | --- | --- |
| 工具参数错误 | 部分适配器将坏 JSON/非对象参数直接判为 provider 失败 | 完整成功响应保留错误参数，统一执行前校验并返回模型纠正；不修补或执行坏参数 | `core/src/tools/parallel.rs`：非 Fatal 调用错误转换为工具结果 |
| 修正后的验收 | 参数改变后签名不同，原始校验错误可能继续阻断交付 | 仅参数准入错误可由后续同名工具成功解除；原报告保留，独立交付验收仍执行 | 采用“可恢复调用错误不直接终止任务”的思路，未复制另一套执行循环 |
| 默认 Open 完成检查 | 隐式合同不允许验收纠偏 | 默认最多 8 轮，失败证据反馈到原任务；显式零轮仍有效 | `core/src/session/turn.rs`：follow-up、待处理输入和停止检查控制循环，具体策略不等同于 Golutra 的轮数 |
| 普通对话 | 一次请求 | 仍为一次请求，不为问候附加检查模型 | 以回归测试验证，不以口号推断开销 |
| 反复压缩与恢复 | 组合夹具验证要求、追加指令及工具配对 | 新增已观察事实、断网期间外部改动、重新读取、后续摘要保留及独立文件验收 | Codex 压缩/上下文重新注入的思想；不宣称夹具证明真实摘要永不丢语义 |
| 工具提前执行 | 完整响应后调度 | 测量真实尾部等待后保留现状 | Codex `OutputItemDone` 可提前生成执行 future；需要权衡终态失败及副作用恢复 |

所有协议仍经过共同的 `ProviderResponse -> ResponseControl -> AgentLoop`。响应失败、工具流未闭合、鉴权失败和未知副作用不会转为可无限重试的参数错误。没有新增后台服务、目标调度器或专用 slash 命令。

## 真实测试条件

- 两端使用 `gpt-5.6-sol`、`medium`、同一 API 网关及凭据、Responses 协议和 unrestricted 权限；工作区分别从同一 jobledger 夹具复制。
- 四阶段依次覆盖多文件实现、恢复/事务与原子保存、长输入 checkpoint、原生后台任务及新进程 resume。
- 同一任务文本，交替执行顺序；不要求子代理，不更改用户正常配置。
- 复用独立判题器及不可修改文件校验；脚本不注入额外修复回合。产品内模型自测与纠错正常计入。
- 保留 runtime 终态、进程退出码和判题结果三种指标；成功退出不等于任务完成。
- 四次用户阶段输入不等于一个无人干预的数小时任务；单组样本不能估计完成率优势或时延 P95 的稳定分布。

复现：

```sh
cargo build -p golutra-agent-cli --bin golutra-agent --locked
python3 scripts/compare_continuous_tasks.py \
  --output /tmp/golutra-continuous-comparison.json \
  --model gpt-5.6-sol --reasoning-effort medium \
  --codex-model-catalog ../project/codex/codex-rs/models-manager/models.json
```

### 第一次测试的兼容性问题

第一次隔离配置运行时，Golutra 四阶段均通过，合计 277.743 秒、29 个 provider 请求。Codex 每次明确报告没有可用的文件/终端工具，实际工具调用为零，因此该组不构成有效的编码能力对比，不能把 4:0 当作胜负。

本地无密钥 HTTP 诊断确认 Codex 请求顶层工具为空。进一步读取其模型目录和 `core/src/client.rs`：该型号默认 `use_responses_lite=true`，工具通过 `additional_tools` 输入项携带。当前网关路径下模型无法使用它们。测试脚本支持临时模型目录，仅将此字段改为 `false`，保持模型、推理设置及其余元数据，切回常规 Responses；不修改 Codex 仓库、全局配置或 Golutra 用户配置。随后重新运行两端任务，Codex 已实际发起工具调用。

首次诊断报告：`/tmp/golutra-continuous-comparison-20260919.json`。该失败记录保留，不混入修正配置后的性能结论。

### 第二次测试发现的真实纠偏问题

常规 Responses 配置下 Codex 四阶段全部通过，合计 369.244 秒。Golutra 的产物四阶段均通过独立判题，但第三阶段耗尽 600 秒基准预算，运行终态仅 3/4 通过，总计 840.433 秒。报告保留于 `/tmp/golutra-continuous-comparison-standard-20260919.json`，这不是一组 Golutra 领先的结果。

实时数据库表明第三阶段一直在执行；导出的 trace 文件是旧快照，最初据此推断“尚未返回首 token”不准确，不能归咎于网络。失败根因是隐式验收把一次失败的探索性 Python 断言永久保留为交付义务，即使后续诊断及产物已经正确；另外，重复补丁路径 `jobledger/checkpoint.py` 被晚期错误字符串分类误导成 checkpoint 故障，令模型做了无关检查。

修正保持 Open 的尽力验证语义：后续必须存在真实成功验证，才不再把可恢复的旧探索诊断当成额外义务；原始失败和 ToolExecution 检查不改写。正式失败测试、显式验证合同、Strict 模式、取消/超时及已知未知副作用不放宽。补丁结构先做无副作用校验，坏参数按前述模型反馈路径处理。新增回归同时验证修正有效及失败测试不能被掩盖，再进行新工作区对照。

### 最终复测结果

修复后使用新工作区重新执行，双方独立判题、运行终态和进程退出均为 **4/4 通过**，基准没有注入修复提示。

| 阶段 | Golutra | Codex | 结果 |
| --- | ---: | ---: | --- |
| 多文件实现 | 119.085 秒 | 99.948 秒 | 双方通过 |
| 恢复、事务、原子保存 | 96.862 秒 | 89.489 秒 | 双方通过 |
| 长输入、checkpoint | 71.822 秒 | 61.239 秒 | 双方通过 |
| 原生后台任务、新进程 resume | 78.844 秒 | 67.787 秒 | 双方通过 |
| 合计 | **366.613 秒** | **318.463 秒** | **双方 4/4** |

Golutra 在本次样本中慢约 **15.1%**，不能宣称全面超过 Codex。之前第三阶段在 600 秒超时，这次约 72 秒正常结束；回归测试与运行证据支持误纠偏问题已修复，但两个模型采样不能用于精确归因提速倍数。

Golutra 的输入 token 为 978,390（未缓存 62,082），输出 24,648，缓存命中率 93.65%；Codex 分别为 1,017,016（未缓存 54,150）、21,949、94.68%。输入总量较少不等于实际费用更低。Golutra 记录 32 个 provider 请求、65 次工具调用；Codex 请求数未知、记录 27 次工具调用。Codex exec/code mode 可合并多个操作，两端计数粒度不同，不把 65:27 当作同口径效率结论。

脱敏后的三轮数据、阶段结果、版本和最终二进制摘要已保存到 [机器可读结果](benchmarks/2026-09-19-continuous-tasks.json)。最终原始报告为 `/tmp/golutra-continuous-comparison-final-20260919.json`；运行时间为 12:34:32–12:46:00 UTC。临时凭据目录已由脚本清理，正常用户配置未改变。

## 提前执行和增量传输决策

最终复测的 28 个有效响应样本合计尾部等待 **843 毫秒**，最大 **153 毫秒**，约占整组用时 0.23%。这仍不支持为此引入提前执行的副作用复杂度。

首次 Golutra 实跑中，25 个响应有明确的工具就绪到终态测量：合计 663 毫秒，最大 86 毫秒，占整组执行时间约 0.24%。这是可重叠区间的粗上界，不是已实现收益；缺失值未计作零，多个并行工具也不能逐个重复累计。

当前没有足够收益依据去引入工具级提前持久化、断流对账及取消竞态，因此保留完整响应边界。HTTP 客户端和连接池继续复用；没有启用 WebSocket 或 `previous_response_id`，也没有假设网关支持状态化上下文。未来只有在同一指标显示实质瓶颈、且上游明确支持对应协议时再实施。

## 验收范围与边界

最终冻结生产源码后的整仓测试退出码为 0：**1931 项通过、4 项忽略，54 个测试组**，其中真实 PTY **27/27** 通过。LLM 定向测试为 94 项单元测试和 34 项本地 HTTP/SSE 测试；这些包含在整仓数中，不能重复相加。比较脚本测试 **64 项通过**。相关六个 crate 的 all-targets Clippy（`-D warnings`）、格式及差异空白检查通过。具体命令和本地日志见 [验收记录](long-task-recovery-acceptance.md)。

本轮新增测试覆盖坏参数后的真实写文件、两次失败验收后成功、显式零轮、语法恢复但结果错误、反复错误的停止边界、一次请求普通对话，以及策略拒绝不获得参数恢复标记。协议矩阵还覆盖常规 Chat 和 direct/auto Responses 的完整坏 JSON 响应，同时保留断流调用不可执行的测试。

默认纠偏不等于自动理解和证明任意需求。它依赖已观察证据、显式合同及配置的验证器；项目验证器发现开关仍遵循原有设置。默认四小时、256 次工具调用及无进展/成本约束仍存在。进程崩溃后的未知副作用仍需对账，不能承诺 exactly-once。

此前两小时真实 TCP 中断测试验证的是恢复机制，不是本轮真实模型连续编码两小时。Windows/Linux 未做运行验收。不能据此宣布长程任务质量全面不输或超过 Codex。
