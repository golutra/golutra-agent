## 首个待验证假设

`objective_evidence.rs` 对直接输入的复合命令先用 shlex 拆词，而显式 `bash -lc` 包装会走已有 Shell AST。于是 `python3 -m unittest ... && python3 -m py_compile ...` 可能把连接符与后续命令纳入 unittest 的 argv 身份；`cargo test || true` 也可能被误当单条测试。执行器与验证器对同一输入的理解不同，是通用正确性问题。

方案：仅让复合语法复用现有 AST 路径，统一包装前后的分类和身份。保留对失败掩盖、零测试、不同测试选择的拒绝；不新增测试命令白名单、复杂脚本解释器或对任意子命令的成功推断。先观察回归在基线上失败，再修复。

## 实验门槛与顺序

1. 确定性回归：直接/包装一致、失败掩盖拒绝、改动后的同一测试能够正常复验、不同测试不能替代、零测试不算通过。
2. 运行时及相关回归、格式、Clippy；冻结候选二进制与摘要。编译不与性能对照重叠。
3. 使用已有任务做基线/候选筛选；新任务作为留出对照，在首次候选冻结前写定提示和独立判题。涉及留出失败的针对性调优后，该任务不得再称未见任务。
4. 同模型标识 `gpt-5.6-sol`、medium、同 Responses 上游；隔离 home/workspace、交替顺序、不人工补发修复提示、不启用子代理。失败全部保留。
5. 接受改动需有可复现正确性收益，或在交付不降质下有性能收益。产品间胜出只描述已测任务；三轮短任务不能证明多小时、所有平台和所有协议全面领先。

主指标是独立交付成功，其次为双方成功配对的总耗时、未缓存输入、输出及模型请求数。Codex 未公开的 provider 请求数保留 unknown；工具项仅作为诊断计数。若新增方案没有改善，则撤销该候选生产改动并保留失败记录，继续调查下一项有证据的原因。

## 优化顺序与不采纳的方案

1. 先让执行器、验证器对同一操作有一致理解。本轮修复有失败回归和真实进程回归，不依赖某个任务名或模型措辞。
2. 用多个领域的独立验收约束质量，再比较成功交付耗时。留出任务为递归配置合并、JavaScript 依赖图、SQLite 原子/幂等/并发转账；各两轮，交换先后顺序。它们用于检查泛化，不冒充数小时任务。
3. 将运行时故障与模型决策分开归因。首轮 Golutra 的三个新任务分别有 80.60/85.14/186.54 秒处于 provider 请求内，占总耗时约 97.7%/98.3%/99.1%。深入事件后发现 SQLite 有一次上游 504，ProviderSession 恢复消耗约 60 秒；最终成功 adapter 请求的 `attempt_count=1` 不等于整个逻辑请求没有重试。需同时检查 `retry_scheduled` 事件，不能只按成功响应诊断下结论。也没有依据为节省本机约 1–2 秒引入流中执行、第二监督模型或更复杂调度。
4. 在相同冻结候选上复查已有多阶段任务，观察修复是否影响验证与交付；不通过人工追加“继续”或修改独立判题挽救失败样本。
5. 真正宣称更强长程能力仍需要跨日期、多次压缩与真实恢复的长任务交付证据。短任务速度、两分钟连接恢复、虚拟时间测试属于不同证据，分别记录。

不采纳批量读文件新 API、减少测试以提速、固定测试命令模板、按样例新增完成规则、强迫模型每次固定复查、降低推理强度。Codex/pi 可借鉴的是简单且可靠的工具闭环；它不要求 Golutra 复制每一个产品策略。

## 第二项根因：补丁语法造成重复生成

六次 Golutra 新任务中，三次因为同一补丁内 `Delete File` 后 `Add File` 被拒绝（依赖图一次，SQLite 两次）。Codex 本地源码 `apply-patch/src/lib.rs:508` 顺序处理 Add/Delete，没有这个统一拒绝条件。Golutra `model_patch.rs` 在前置解析阶段拒绝所有重复路径，要求模型重新生成同一内容；SQLite 首轮重写消耗一个 21.4 秒、3016 输出 token 的请求。这是工具合同摩擦，与任务领域无关。

方案是仅将相同原始路径的 `Delete → Add` 合并为一次 Replace，再复用统一 diff、整批校验、checkpoint、权限及原子应用。不是顺序执行真实删除；不放宽 Add 覆盖已有文件、反序 Add/Delete、重复更新和词法路径别名冲突。可保留原文件执行权限。

先加入真实文件回归，两个正向回归在原实现失败；从原始 provider response artifact 取回 10932 字节失败补丁，原解析器同样报重复路径。保留此失败，再实施通用语法适配。

由于已根据依赖图和 SQLite 轨迹改进工具，这两项以后属于开发集，不再称未见任务。新增 interval_ranges 在第二候选构建前冻结，包含半开区间归并/差集、任意大坐标、严格输入验证与 CLI，使用独立点集 oracle 验证 100 组小范围随机输入，并单独验证大坐标；摘要 `e24ff4433331dd015b4db3d0577342769c46df63324c8bc35f7cefc4dc3a4c8b`。

第二候选的生产解析器成功处理原始 10932 字节补丁，生成三个文件的统一 diff；经 `git apply --check`、实际应用、同一 SQLite 独立验收和生成的回归测试均通过。第一次模型产物本身正确，失败来自工具适配。复验位于 `/tmp/golutra-generalization-review.aMZ5dH/patch-replay`；存档仅补上末尾换行，未改变补丁操作与正文。原始补丁摘要为 `c92d5fd0997b391c9c71b47023454528a50e34c91a726902b27cfa86065ab960`。

## 收尾发现的验证上下文边界

源码复核发现 `cd one && cargo test` 与 `cd two && cargo test` 会生成相同身份；新增回归在第二候选源码上实际失败。另将执行器报告的实际 `workdir` 纳入身份，统一预计算元数据和报告回退路径，避免不同子项目之间错误互相复验。

第一次尝试将验证前所有准备命令都计入身份，通过了新用例，却破坏原有 Git 修复后复验回归：修复文件的操作不同，不应使同一个 `git diff --exit-code` 变成不同检查。这版不保留，原回归断言未改。最终改为保留 Shell 赋值、`cd`、`read`、`printf -v` 等改变 Shell 上下文的内建操作；普通外部进程不能改变父 Shell 上下文，其工程文件修改仍由现有验证新鲜度机制处理。最后一次验证后的非验证尾部不计入身份。这里按 Shell 语义区分状态变化，不按任务名或基准样例制定策略。

这进一步收紧错误等价，不代表可以证明任意 Shell 程序的完整语义。先前实跑数据继续绑定各自二进制，不冒充这次收尾修复后的新构建。
