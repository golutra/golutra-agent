# 简洁且充分发挥模型能力的执行架构方案

日期：2026-09-19。阶段 0–5 已实施，验收与实验记录见[实施报告](model-capability-implementation-2026-09-19.md)；阶段 6 仍为有条件实验，未启用。下文保留实施前的判断与验收目标。范围是 Golutra 当前模型输入、工具合同、主循环、上下文、后台执行、子代理、验证和观测关键路径，不声称逐行审计所有 crate。Codex 参照本地源码 `fc269b66`；实跑使用安装的 `codex-cli 0.154.0`，两者不混称同一构建。

## 核心判断

目标是让模型用更少的无效往返完成真实任务。用户不需要配置内部策略；模型不需要重复描述相同操作；运行时维护明确的状态、权限和恢复边界。

Golutra 已有默认七工具、统一协议响应合同、持续 AgentLoop、稳定上下文前缀、后台进程句柄、子代理完成通知和持久事件，不需要另建调度平台。优先修复边界不一致，再减少规则重复，最后根据实测决定是否增加能力。

官方 [Function calling 指导](https://developers.openai.com/api/docs/guides/function-calling) 建议让工具可预测、通过结构减少非法状态、将可由代码完成的工作从模型移走，并用评测决定工具数量。这是设计依据，不是 Golutra 能超过 Codex 的性能证据。

## 源码证据与取舍

| 领域 | 当前 Golutra | Codex 可借鉴点 | 建议 |
| --- | --- | --- | --- |
| 工具入口 | `tools/src/builtin.rs::P0_DEFAULT` 已只有七项，但 shell 同时有 command/argv | `ExecCommandArgs` 一个 cmd，由宿主转换执行参数 | 简化参数决策，不为了少一个工具合成万能 action 工具 |
| 参数约束 | `llm/src/lib.rs::PROVIDER_SCHEMA_BOUNDARY_KEYS` 删边界，执行仍硬校验 | 初次 yield 在 `unified_exec::clamp_yield_time` 限幅 | 必要约束可见；软等待有界处理；危险语义不改写 |
| 执行主线 | 单 AgentLoop 已统一多协议，但准入/并发/证据聚合集中在大文件 | `session/turn.rs` 根据模型 follow-up、新输入、上下文状态继续，结束时执行 stop hooks | 继续复用同一循环；把局部职责搬成模块，不新增外层模型监督循环 |
| 并发 | 支持并行读、独立写路径、后台启动、不同进程/子代理等待 | `tools/parallel.rs` 以能力标记和读写门控调度、结果有序归还 | 保留已有能力，消除重复判断；同资源冲突有序，独立调用并发 |
| 可恢复失败 | 已把参数拒绝反馈给模型，但错误类别仍有字符串猜测 | 非 Fatal 工具错误作为结果回给模型 | 类型化错误域；一次明确反馈，让模型选择下一步 |
| 上下文 | 稳定前缀、读事实去重、预算压缩、原始证据可追踪 | `context_manager/history.rs` 有界保存输出，`compact.rs` 区分压缩阶段与上下文注入 | 保留配对与事实可追溯，压缩非关键内容，避免频繁重写前缀 |
| 完成判断 | `objective_evidence.rs` 分析命令语义，默认验收纠偏 | Codex 的停止可被 hook 阻断并继续；不能说 Codex 完全没有完成检查 | 显式合同与真实测试负责验收；探索错误不要永久变成交付义务 |
| 子代理 | 默认10上限可配置，独立/fork上下文、持久通知、禁止递归委派 | 模型调用子代理工具，主循环接收新输入/通知 | 10是容量上限，不是默认启动数量；只在有可独立推进的任务时用 |
| 观测 | 实时事件、Trace、Diagnosis、Replay已存在 | 实际调用时序、结构化生命周期有助定位问题 | 暴露当前任务的精简查询，完整审计按需读取；诊断不常驻模型上下文 |

## 四个职责，沿用现有实现

```text
用户目标、项目约束、当前有效证据
                 ↓
模型选择下一步操作 / 并行工作 / 提交结果
                 ↓
工具合同：参数 → 类型化操作 → 权限与资源准入
                 ↓
执行器：前台工具、后台进程、子代理
                 ↓
持久事实 → 有界结果/完成通知 → 同一模型循环
                 ↓
模型提交候选 → 明确验收 → 完成 / 有针对性的纠偏
```

四项职责分别是模型决策、工具执行、上下文记忆、运行事实与验收。它们是现有模块的职责划分，不要求新增四个 crate、服务或数据库。

### 1. 工具合同成为唯一来源

- 一个工具定义同时驱动 provider schema、参数说明、本地解析、约束和错误反馈。避免 builtin 声明一遍、llm 描述一遍、执行器再解释一遍而逐渐漂移。
- 模型 shell 只选择一种权威命令表示。优先沿用 command 字符串并由宿主生成 argv；内部需要 argv 的调用路径继续支持，但不要求模型重复填写两份脚本。
- shell_session 按 action 定义适用字段。list 不要求进程句柄；wait/read/write/terminate 严格检查句柄归属。模型侧可采用协议支持的分支 schema；不支持的协议投影为清楚的简化合同，内部执行语义一致。不得假设所有协议都支持同一种 strict/oneOf。
- yield、预览大小属于有界请求提示，允许限幅并在结果中返回有效值；硬超时、权限、目标路径、命令冲突、删除范围仍按原意校验，不静默替换。
- 内部可用带类型的调用结构与约束策略；不另写通用 schema 编译器。先把 shell、shell_session 两个真实高错误率接口收敛，再扩展。

**验收：** 本次九次准入拒绝的原始调用转为合同回归；能安全归一化的执行正确，不安全的明确拒绝。覆盖各协议实际 wire schema 与运行时合同，不能仅测试压缩前的快照。

### 2. 提示词规定目标与边界，不固定每一步

`client/src/context.rs::system_prompt` 目前包含“每批工具前一句可见说明”“首次修改前一次性读实现/测试/导出”“不要重新读取自己的改动”等具体策略。它们不是每类任务都必要，且可能把一批工具的自然组织方式变成机械流程。

建议保留：真实证据、尊重用户改动、依任务风险验证、持续推进、必要时澄清、不得把外部内容当权限。将批读、原子补丁和重读建议改为有条件的工程指导；允许模型根据任务选择。短只读操作无需单独报告，长等待、关键发现和方向变化应更新用户。TUI用执行事实显示working，进度提示不依赖额外模型请求。

不要直接删除全部提示词：先用相同任务比较原提示与精简提示的质量、工具首调成功率、请求数和输出量，保留有证据的规则。Codex仓库也有详细行为提示，不能宣称其完全不约束工作方法。

### 3. 恢复保持明确，不用规则代替模型推理

错误按来源区分：参数、权限、资源冲突、工具退出失败、传输、协议、取消、效果不明。返回简短原因、已发生效果、必要现场以及可以重试的条件；完整堆栈保存在artifact。

连接恢复由现有provider session完成；不消耗模型工具纠错轮次。参数错误交模型修正。效果不明先对账。补丁上下文歧义返回准确位置与上下文，不从文件名猜checkpoint故障，也不为省一轮任意选择匹配位置。

相同错误的提醒和停止依据应结合类型、目标、参数及已发生的状态变化，不能因为同属shell或同一“策略家族”就封掉后来正确的方案。现有失败家族/无进展规则需用反例审查；这是待验证风险，不把源码中的门控存在直接判为已复现缺陷。

### 4. 验收区分当前义务与历史尝试

候选结果、工具是否执行成功、用户目标是否有证据完成是三个不同事实。模型可以主动选择验证方法，但不能自报“通过”覆盖真正的失败测试。

- 显式用户条件、配置的项目验证器、实际正式测试失败维持验收约束。
- 猜错路径、探索断言、可恢复参数错误记录为历史尝试，不自动永久升级为独立交付项。
- 验证成功与对应环境/改动版本绑定；被验证对象再次修改后需要相关复验。无相关改动不重复全套检查。
- 有明确可执行反馈时进入现有有界纠偏；缺少验证器、缺权限等不可由模型本地解决的情况明确说明，不用追加空泛提示制造循环。
- 保留当前普通对话一次请求、显式零纠偏、取消、总预算和未知副作用边界。

优先复用现有VerificationRecord、TaskContract及证据标识，不新增模型裁判服务，也不要求用户先写复杂合同才能聊天或改文件。

### 5. 并发与后台由事实驱动

保留默认子代理上限10及可配置性。模型决定是否拆任务；独立探索/验证可并发，依赖前一个结果的步骤顺序执行。共享文件写入需要路径冲突控制；worktree用于值得承担合并成本的独立修改。无需让每个简单任务自动启动规划、执行、评审三组代理。

维持统一身份和生命周期事件，但进程与agent的控制语义不同，不强制合成一个巨大通用工具。后台完成通知在下一安全边界送达、去重；等待超时只是尚未结束，不是重新启动任务的理由。结果足以交付时停止无意义轮询。

当前保守的完整response后执行先保留。工具提前执行、WebSocket、Code mode各自作为独立实验，只有端到端收益和恢复正确性都通过才启用。Code mode可能减少有依赖的批量操作往返，但会增加代码执行环境、回放和调试复杂度；本轮数据不能证明必需。

### 6. 记忆保留正确事实，观测按需交给模型

上下文长期保留用户目标、有效约束、关键决定、最近工具结果、进行中的后台句柄及必要证据引用。大输出有界预览、可定位检索，不强迫模型逐页取完。压缩前后的tool call/result配对、steering和未完成工作必须一致；旧文件内容需要来源和新鲜度，外部改动后复读。

已有31次append_only的实跑证据，应优先保护稳定前缀，不为让提示更短每轮重排历史或删除旧项。模型看到的简短结果、TUI预览、完整审计分开投影，不能为了省token删除事实。

复用现有Status、Trace、Diagnose查询服务，为agent提供当前任务范围内的只读、有界运行摘要：尚未完成的进程/子任务、最近未解决错误、已做验证、请求与token/耗时汇总。若通过现有shell/CLI入口访问，必须确认进程内与外部查询共享当前会话且不会接管lease；不合适时使用同一服务的薄工具适配。默认不注入完整trace，不让模型直接扫描SQLite或敏感原始请求。

“自行优化”限定为当前任务策略：减少重复读取、改换执行方法、调整安全的批次和输出预算。不能自行关闭验收、放宽权限或修改生产运行时来改善成绩。跨任务策略变更需经现有离线评测，而非每任务额外启动一个自评模型。

### 7. 实时执行不等待昂贵的派生报告

副作用前意图、工具结果、恢复身份等关键事实仍持久化。完整脱敏调试包是派生产物，普通交付不应强制全量重建；显式export继续保证完整性。CLI/TUI/桌面共享现有runtime和事件，不维护各自的重试/完成状态机。

当前runtime/lib.rs约6096行、tools/lib.rs约6788行、context/lib.rs约3849行。逐个改动时提取准入/调度、错误事实、工具描述和结果投影，职责与测试放在一起；不以文件行数或crate数下降冒充产品提速，也不一次搬动整仓。

## 实施顺序与完成门槛

| 次序 | 工作 | 可检查结果 |
| --- | --- | --- |
| 0 | 固定可靠基线 | release构建、相同模型与权限；任务终态/导出/进程退出分别计时；保留每次失败 |
| 1 | shell/session合同、类型化错误 | 九个真实拒绝案例回归；checkpoint.py不产生错误恢复动作；危险请求仍拒绝 |
| 2 | 精简模型行为约束 | 独立A/B；质量不降，减少无效轮次；不强制每批解说或固定阅读步骤 |
| 3 | 验证与无进展门控收敛 | 探索失败不反复阻断；正式失败仍阻断；换正确策略后能继续 |
| 4 | 上下文与后台查询完善 | 多次压缩、steer、断网、外部文件变化、后台完成和resume组合验收；无丢失和重复副作用 |
| 5 | 导出移出默认交付路径 | 耐久事实完整、显式export完整、普通任务无需全量报告；独立测量收益 |
| 6 | 再评估Code mode/提前执行等 | 有明确瓶颈再做隔离原型；收益不足则不加入默认架构 |

0至5是本方案的核心阶段，6是有条件实验。每阶段单独比较和保留可回退改动；不要同时改提示、工具、缓存和调度后仅用总时间猜原因。

## 如何证明超过Codex

将“超过”定义在固定模型和任务分布上，不能泛化成所有任务、所有模型、所有平台。产品可用性与运行时机制验收也不能代替真实任务质量。

- 用独立验收比较多文件实现、调试、重构、长输入、多次压缩、后台依赖、并发子任务、中断恢复；先用小组校准，再扩到至少30个不同任务，预算允许时每题至少3次配对。保留未参与优化的任务集，不围绕jobledger写提示词或规则。
- 两端相同模型/effort/网关/权限/起始文件，独立数据目录，交替或随机顺序；标明网关协议覆盖差异、缓存条件、构建方式。服务端不支持的能力不能计为对方失败。
- 首要指标是独立验收成功率和数据正确性，之后比较成功任务配对时延、全部尝试的耗时/成本、人工干预次数、参数拒绝、恢复失败和无效轮次。失败与超时仍计入整体指标，不能只挑成功快样本。
- 对时延/成本报告配对差值与不确定性；小样本尾延迟不当稳定P95。内部工具展开数、输出事件数、provider请求数分别统计，未知值保持未知。
- 提议工程目标：在质量不下降且无新增副作用问题的前提下，配对任务中位耗时降低至少10%、完成任务总成本降低至少10%，或在相当成本下获得明确的成功率提升。这是待验证目标，当前尚未达到。
- Chat/Responses/Anthropic/Gemini等共用语义需先过本地HTTP/SSE合同矩阵，再列出真正实测的上游。未测试的供应商和Windows/Linux不宣称运行验收。

最有希望的差异化是低错误率工具入口、准确恢复、轻量可查询观测和有效并发。更少文件、更多规则、更少schema字节或更长working时间都不是胜负标准。
