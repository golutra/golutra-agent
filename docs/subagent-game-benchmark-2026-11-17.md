# 子代理真实游戏任务：并行与串行实测

日期：2026-11-17，Asia/Shanghai。测试对象是当前工作树中的 Golutra runtime，使用真实 provider 和真实子会话。此前子代理重构的单元、进程和协议测试见 [实施验证记录](subagent-validation-2026-11-17.md)，这些历史测试数量不计入本报告。

后续实现与独立复测见 [子代理优化验证](subagent-optimization-2026-11-17.md)。以下保留优化前的测量和缺陷，修复版游戏不覆盖原始计时产物。

本次让 Golutra 独立构建两份 ORBIT BREAKER 太空生存射击游戏。并行组八个子代理全部完成，实际峰值并发为 8，端到端耗时 177.589 秒；串行组峰值为 1，耗时 783.002 秒。两组均通过外置验证器的 23 项检查，也能在真实浏览器中移动、射击、得分、暂停、死亡和重开。

这证明当前子代理能完成有实际文件产物的并行工作。串行组遭遇四次上游 504，样本每组仅一次；4.41 倍是本次观测值，不能视为调度器固有提速或重构前后的提升。界面仍有重影、遮挡及状态反馈缺陷，尚不能称为完整产品验收通过。

## 游戏和任务拆分

游戏采用原生 Canvas、ES modules 和 WebAudio，没有 npm 运行依赖、CDN 或远程素材。操作为 WASD/方向键移动、鼠标瞄准、空格或鼠标左键射击、P/Escape 暂停；有生命、波次、计分、补血和重新开始。

两组使用相同的预先冻结的 `CONTRACT.md`，明确状态结构、模块导出和文件归属。任务拆分由测试准备阶段提供，因此本次衡量的是按既定边界执行与整合的能力；没有测量模型从模糊需求自主拆分八个模块的成功率。

| 执行者 | 负责文件及功能 |
| --- | --- |
| input | `input.mjs`：键鼠、坐标转换、失焦清理 |
| player | `player.mjs`：移动、斜向归一化、边界与无敌时间 |
| combat | `combat.mjs`：射击、冷却、子弹生命周期 |
| enemies | `enemies.mjs`：确定性生成、追踪、波次 |
| collisions | `collisions.mjs`：碰撞、伤害、计分、补血、死亡 |
| renderer | `renderer.mjs`：Canvas 图形与反馈 |
| ui | `ui.mjs`、`styles.css`：HUD、菜单、按钮与布局 |
| audio | `audio.mjs`：程序音效、静音、无音频环境降级 |
| 主代理 | `game.mjs`、`main.mjs`、`index.html`、`README.md`：整合、检查和必要修正 |

并行组要求八个 `run_in_background:true` 子执行先派发，再等待；串行组要求逐个 `run_in_background:false` 完成。实际返回的并发上限分别为 8 和 1，各有八个独立子 session，全部完成。未发现跨组读取游戏源码，写入均在本组工作区内；未手工修改生成的游戏代码。

## 测试口径

- Provider 为既有 `golutra` 配置，模型 `grok-4.7`，通过 SDK Prompt 显式指定 `reasoning_effort=low`；两组父子任务创建记录均确认实际为 low。
- 使用同一个 debug 可执行文件、同一合同、同一个工作区外验证器和隔离的持久 runtime 状态。凭据仍走既有 SecretRef，没有修改全局 provider 配置。
- 顺序为并行组、串行组，每组一次。没有随机化顺序、反复取最好成绩或运行重构前版本。
- 端到端耗时来自 runner 单调时钟，覆盖启动、任务执行和 driver 关闭。任务中注册的外部验证包含在内；退出后的复核和浏览器 QA 不在该耗时内。
- 子执行耗时来自持久化 `TaskCreated` 到终态。峰值并发是这些区间的最大重叠数；平均并发是子耗时总和除以至少有一个子执行活跃的时间，并非 CPU 利用率。
- 验证器在游戏工作区外，原文件和合同哈希未变；代理允许运行并读取验证器，本次不是隐藏题评测。23 项覆盖模块接口、实际状态变化、输入监听和绘制调用，浏览器交互另行验证。

### 实际重叠与主代理开销

相对各自主任务创建时刻，单位为秒：

| 子执行 | 并行开始 | 并行结束 | 并行耗时 | 串行耗时 |
| --- | ---: | ---: | ---: | ---: |
| input | 100.034 | 154.032 | 53.998 | 94.615 |
| player | 100.118 | 110.143 | 10.025 | 19.154 |
| combat | 100.135 | 148.583 | 48.448 | 35.906 |
| enemies | 100.160 | 149.286 | 49.126 | 65.307 |
| collisions | 100.198 | 147.818 | 47.620 | 109.130 |
| renderer | 100.244 | 140.074 | 39.830 | 108.360 |
| ui | 100.286 | 159.417 | 59.131 | 137.338 |
| audio | 100.345 | 118.499 | 18.154 | 80.121 |

八个并行子执行在 0.311 秒内全部进入执行。不同归属文件的写入没有把任务退化为串行；活跃窗口内平均占用约 68.7% 的八个子执行名额。该比例受任务长短不同影响，不能据此诊断调度空转。

并行主任务前 100.034 秒尚无子执行，随后子任务窗口 59.383 秒，最后整合与收尾约 16.682 秒。第二个主代理响应同时生成八个派发调用和四个整合文件写入：传输诊断记录该响应 97.145 秒，其中最早工具就绪至响应结束 68.167 秒。当前工具派发等待整条响应完成，模型把整合代码放进同一响应，延迟了并行工作的开始。

低风险优化方向是让主代理先发简短的八个委派，再在下一轮生成独立整合文件，使生成阶段也能和子代理重叠。本次没有实施或测量该优化，也没有引入响应未结束就提前执行工具的行为。

串行组首个子执行在 18.945 秒开始，最后一个在 724.684 秒结束；其间 705.739 秒中子执行活跃 649.931 秒，剩余约 55.808 秒包含主代理轮次与派发间隔。

## 实际浏览器验收

使用已安装的 Ego 原生浏览器，在同一个测试 TaskSpace 中分别打开两组产物。实际发送键鼠输入，读取只读游戏快照和页面状态，并检查截图；没有通过修改游戏状态来制造通关或得分。

- 两组均能点击 Start、真实移动、瞄准射击、击杀得分，Pause 后时间保持不变，Resume 后继续；自然接敌后生命降至零进入 game over，Restart 重置生命、分数和击杀数，Escape 可暂停。
- 移动观测为并行 `x=480→590.084`、串行 `480→581.504`；两组实际击杀数 1、分数 10。测试窗口内未捕获 `Runtime.exceptionThrown`。
- 串行组静音按钮点击后仍显示 `Mute`，也没有状态标志，因此该检查失败。源码确实调用了 `audio.setMuted(muted)`；本次证据是缺少状态反馈，不能扩大为“音频静音失效”。未做声学输出测量。
- 420×840 下两组 Canvas 均在视口内，开始按钮可达；截图进一步发现串行 HUD/按钮遮挡标题，并行标题层透出 HUD，两组都有 Canvas 与 DOM 重复标题造成的重影。边界框检查通过不等于视觉验收通过。

11 项脚本检查包含异常捕获、状态和按钮检查；截图缺陷单列，未塞进该分母。没有测量手机触控、长时帧率、内存增长或所有浏览器兼容性。

## 本次暴露的问题与后续方向

| 观察事实 | 影响与建议 |
| --- | --- |
| 首次派发迟至第 100 秒 | 优先拆开委派响应和大段整合代码；端到端效率需要一起观察模型生成与执行重叠 |
| 并行组完成总结后，又消费一次合并后台结果并请求模型 | 已实现合并，未发生八次逐个唤醒；但结果已由 wait 返回时仍有一次重复总结，建议按具体子 execution 对齐观察与消费，保留真正新结果的交付 |
| 引用给子任务的“no tools”会影响父任务 | 既有全局关键字匹配不理解作用域；应将工具策略绑定明确任务配置，避免从任意引用文本关闭父工具 |
| CLI 与 TUI 的 reasoning 默认配置入口不同 | 本次测试最初错误假设项目 runtime.json 对 exec 同样生效；建议统一配置入口或明确展示实际 effort，测试必须核对任务事实 |
| 功能检查通过仍有菜单重影/遮挡 | renderer 与 DOM UI 的菜单职责需明确，整合验收补状态反馈和真实截图检查 |

并行重复总结的具体证据为 UTC `18:19:31.402585` 首次总结、`18:19:31.485794` 后台消费、随后一个输入 37,306/output 85 token 的请求（传输终止诊断 2.351 秒），`18:19:33.770829` 第二次简短总结。两组均只有一次 `BackgroundResultsConsumed`；本次未实测运行途中插入用户输入的竞争场景，该边界仍以既有确定性测试为证据。

全局禁工具判定在 [runtime 的 objective_disables_tools](../crates/golutra-agent-runtime/src/lib.rs)，使用 `normalized.contains("no tools")` 等关键字，HEAD 已存在；不是本轮子代理重构引入的新缺陷。[运行入口文档](runtime-entrypoints.md)明确把 runtime.json 的 reasoning 默认规则描述为 TUI 规则，因此 exec 参数误配同时是本次测试准备问题，不能笼统归为新生产回归。

| 运行 | 实际结果 | 是否进入正式对比 |
| --- | --- | --- |

| probe2 | 调整作用域措辞后，真实子 session 返回 323；主任务 10.415 秒，子执行 2.797 秒 | 否，仅连接与委派预检 |
| parallel（CLI / high） | 10 分钟仍未派发子任务，按已宣布的无进展截止策略发 SIGINT；进程总耗时 621.748 秒，主任务 617.367 秒后取消，没有游戏产物 | 否。保留取消失败样本，不计入成功耗时 |
| parallel-low（CLI） | 项目文件请求 low，但实际任务仍为 high；发现配置不符后在 50.135 秒终止 | 否。配置无效样本，不能称 low 的性能结果 |
| parallel-sdk / serial-sdk | 显式 Prompt 配置，两组父子实际均为 low，真实完成游戏与验证 | 是，各一次 |

high 样本有一轮响应长达 286.063 秒，输出 20,373 token，其中推理 20,338 token，最终只发出文件读取；已完成五个请求共记录 72,103 token，另有中止的在途请求用量未知。这说明默认 high 在该次任务中可出现严重的首派发拖延，不能因后续 low 成功而忽略；单次观测无法分离模型、上游速度和提示策略的贡献。

正式并行组两次工具错误：主代理将 `wait_ms` 设成 180000，被 60000 上限拒绝后纠正；combat 子代理的一次自测使用 1 秒步长后访问已过期/出界子弹。串行组五次错误：父路径漏前导 `/` 两次，input 子代理自检/提前验证两次，ui 子代理在主入口未写完时执行完整验证一次。最终验收结果保持独立记录，未用忽略断言或人工补游戏代码消除失败。

计量曾仅看 transport attempt_count 而漏掉 runtime 重试；最终按 `(session, provider_request_id, attempt)` 去重 `RetryScheduled` 的 retrying 阶段，得到四次。waiting/retrying 两阶段共八条事件，不能计成八次重试。
