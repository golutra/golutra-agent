# TUI 稳定性：实施、撤回实验与对照验收

本轮延续已有的 Markdown/输入缓存优化，处理剩余的重复投影和事件调度问题。对照源码是 Codex `fc269b66`，对照可执行程序为已安装的 `codex-cli 0.155.1`，两者不能假定完全一致。测试环境为 macOS ARM64、本地 Responses SSE、120×32 真实 PTY；没有调用真实模型。

## 最终保留的实现

| 工作项 | 实施及边界 |
| --- | --- |
| 阶段计时 | `ui_timing.rs` 可选记录事件应用、批次、投影、历史、帧、终端 flush、输入处理、快照应用。最多保留最近 16,384 个阶段样本，退出后落盘，不收集文本、按键或凭据 |
| 历史记账 | 新增时只计算新事件的大小；回放替换重算一次，裁剪减去被移除事件。所有生产清空路径通过替换入口重置计数，不再每 256 个事件扫描全部历史 |
| 活动正文 | 连续同回合 delta 直接追加到已缓存的活动助手条目；普通布局和流式归档行数变化保留投影。重试、工具、最终文本、历史替换、裁剪或命令边界变化回退完整投影 |
| 工作预算 | 交互应用事件每批至多 32 个，逐事件检查 2ms 预算。保留 FIFO，剩余事件会主动唤醒，不依赖网络再来一个事件。单个事件不可抢占；离屏 driver 仍完整同步 |
| 公平调度 | 对照 Codex `tui/event_stream.rs` 的轮转机制，绘制、键盘和 Runtime 就绪源轮流获得优先机会。继续沿用现有 120 FPS 上限和合并截止时间 |

相关实现：`crates/golutra-agent-tui/src/{ui_timing,fair_select,runtime_controller,transcript_view,main}.rs`。没有增加 provider 协议分支、后台服务、鼠标捕获或用户配置开关。

## 没有保留的逐行排队实验

Codex `streaming/{mod,chunking,controller,commit_tick}.rs` 将稳定行入队，平时逐行提交，达到深度或年龄阈值后追赶；这与可变尾部、提交动画和独立历史 cell 配合工作。此次实际实现过一个小队列，只保存行年龄，采用 8 行/120ms 追赶条件，并为完成、`/status`、覆盖层进入保留强制排空路径。

第一版让可变尾部越过待提交稳定行，PTY 回归观察到末尾 `STREAM_DONE` 已出现而倒数一段尚未显示。修正为连续可见前缀，并直接归档已经预览过的行后，完整测试通过；但紧邻 A/B 的突发场景仍明显变慢：

| 同条件突发输出 | 中位数 | P95 | 最大值 | 观察到的标记 |
| --- | ---: | ---: | ---: | ---: |
| 本轮修改前 | 16.51ms | 31.72ms | 32.78ms | 400/400 |
| 逐行排队候选 | 30.18ms | 67.22ms | 73.79ms | 400/400 |

因此最终源码删除该队列及其状态，不保留隐藏开关。稳定前缀继续按帧批量归档，未换行正文实时预览；采用工作预算和公平调度解决输入竞争。这里的否定结果属于完成验证后的设计决策，不能宣称逐行动画改善了 Golutra，也不能把 Codex 的 120ms 追赶阈值解释为端到端延迟保证。

## 阶段计时与旧的 229ms 样本

本轮先对原有行为加计时，400 个段落片段全部观察到。该轮端到端 P95 为 7.12ms、最大 25.46ms；阶段统计如下：

| 阶段 | P95 | 最大值 |
| --- | ---: | ---: |
| 事件应用 | 0.041ms | 2.132ms |
| 事件投影 | 0.402ms | 1.060ms |
| 历史归档 | 3.516ms | 6.737ms |
| 整帧（包含内部阶段） | 4.105ms | 7.695ms |
| 帧末 flush | 0.002ms | 0.005ms |

阶段有嵌套，不能相加；flush 也不代表用户终端 GPU 已完成显示。这一轮没有复现此前的 229.12ms 离群值，因此不能将它归因于 256 事件扫描、UI 单帧或模型。测量工具另行记录 Python 屏幕解析耗时，并保存单调时钟到 epoch 的映射，便于复现时关联阶段日志；保留旧样本和未确定的归因。

最终版本另外启用计时重跑“40 轮历史 + 突发输出 + 并行键入”：仍为 400/400，输出 P95 24.50ms、最大 67.57ms，输出期间输入 P95 6.95ms。最后 16,384 个阶段样本中，事件应用 P95/最大为 0.204/1.821ms，事件批次为 0.164/1.823ms，整帧为 5.639/25.946ms。关联首批 67ms 等待区间，该区间内最长帧约 3.37ms；这排除了“整个等待都是一次长帧”的解释，但没有进一步分解上游处理、Runtime 投递与调度间隔。全程帧最大值和首批等待属于不同样本，不能混为一个瓶颈，也不能用这次结果解释旧的 229ms。

## 验收与可复现性

最终同条件对照（每格为中位数 / P95，单位 ms；每种场景 400 个片段）：

| 场景 | 修改前 Golutra | 最终 Golutra | Codex 0.155.1 |
| --- | ---: | ---: | ---: |
| 中文段落 | 5.52 / 7.78 | 5.13 / 6.44 | 62.74 / 98.48 |
| 代码块 | 10.05 / 16.62 | 9.46 / 13.78 | 11.88 / 12.95 |
| 无换行长单段 | 11.70 / 18.94 | 11.48 / 20.98 | 不作延迟排名，屏幕采样仅观察到 45/400 |
| 每 200ms 突发 8 片段 | 8.45 / 22.03 | 7.21 / 19.64 | 2.62 / 3.11 |

Golutra 前后两组均每场景观察到 400/400。最终最大延迟依次为 27.98、26.99、29.57、31.41ms；对应修改前为 27.28、27.95、30.50、25.65ms。并非所有尾延迟都变好：长单段 P95 与突发最大值仍略差，不能只选择有利指标。Codex 的段落与无换行文本预览/提交策略不同；45/400 表示此屏幕采样方法没有在生成期间逐一看到所有标记，不证明持久文本缺失。该不完整观察保留在原始结果中。

40 轮相同历史后，再输出 400 个突发片段并同时键入（每项 30 次按键）：

| 指标（中位数 / P95，ms） | 最终 Golutra | Codex |
| --- | ---: | ---: |
| 长历史下普通输入 | 3.04 / 3.37 | 23.52 / 24.24 |
| 输出期间输入 | 3.05 / 7.59 | 23.89 / 25.64 |
| 输出片段延迟 | 10.20 / 23.75 | 2.92 / 13.55 |

两者均观察到 400/400 个输出标记；输出最大延迟为 68.07/60.65ms，输入最大延迟为 13.91/31.17ms。这个样本支持 Golutra 的输入没有被模型流饿死，但 Codex 的突发输出仍更快。每个场景是有限次数的本地测量，不构成普遍领先或数小时稳定性的证明。屏幕解析器在最终全部场景中的单次最大耗时不超过 1.19ms，不能据此倒推旧测量的观察器耗时。

完整摘要见 [原始结果 JSON](2026-09-21-tui-stability-results.json)，包括被撤回的候选。

最终 Rust 全组 458 项通过：19 lib、404 TUI、28 PTY、7 driver；1 项真实上游 smoke 按既有规则忽略。Clippy 全目标 `-D warnings`、Rust 格式、diff 检查及基准脚本 Ruff 检查通过。新增回归覆盖字节计数的裁剪/回放/重置、连续增量与规范回放的等价性、重试和最终修订、三来源公平性、预算耗尽后无新网络事件仍继续消费；原有真实 PTY 继续检查完整有序正文、resize、`/status`、resume、覆盖层和草稿。
