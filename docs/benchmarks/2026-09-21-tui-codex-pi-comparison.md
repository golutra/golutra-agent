# Codex、pi 与 Golutra 的流式显示对比

## 取证范围

2026-09-21，直接阅读本地 `../project/codex`（`fc269b66`）和 `../project/pi`（`dbb9911a`），两份参考仓库工作区均干净。Golutra 基于上一轮 TUI 优化后的工作区继续实施。源码分析不等于这些版本的实机性能排名，也不能把本地 Codex 源码与已安装的 Codex 0.155.1 当成同一实现。

流畅度需要分别看：输入回显、首段等待、持续显示间隔、突发追赶、正文变长后的计算成本、闪烁/重排和内容完整性。网络或模型没有送来内容时，TUI 无法凭空补字；刷新频率上限也不是实际达到的帧率。

## 源码对比

| 路径 | Codex | pi | Golutra（上一轮完成时） |
| --- | --- | --- | --- |
| 刷新调度 | `FrameRequester` 合并请求，最早 deadline 生效，120 FPS 上限 | `requestRender` 合并重复请求，`scheduleRender` 按上次绘制时刻保证约 16ms 最小间隔 | `FrameScheduler` 合并请求，120 FPS 上限；首个有意义事件可立即请求绘制 |
| 内容推进 | 完整源行进入 collector；稳定行队列正常每 tick 推进一行 | 更新当前 assistant message，重建其中的 Markdown 组件，再请求刷新；没有对应的逐行提交动画队列 | 接收有序 runtime 事件，绘制时展示最新累计内容，不额外排逐字动画 |
| 突发输出 | 深度达到 8 行或最老行等待 120ms 时进入 catch-up，一次清空当时积压；有退出和再进入滞回 | 同一帧前的更新合并，显示最新内容 | 同一帧合并显示；维护批次最多处理 32 个事件，返回输入/绘制调度 |
| Markdown | `StreamingRender` 保留稳定块，只解析可变尾部；开放代码围栏有追加路径；引用定义等全局影响回退全量 | Markdown 按文本和宽度缓存；文本变更后重新 lexer 和排版。当前消息更新会重建子组件，因此不能声称它是完整增量解析器 | 已复用语义相同块的排版和代码行，但每次内容变更仍完整解析；归档还单独解析块边界 |

| 表格/嵌套块 | 明确的 table holdback；表格列宽可能随新增行变化，不能提前冻结 | 当前组件全量重新排版；最终按行差分写屏 | 可变块重排；只归档匹配的稳定前缀 |
| 历史 | 已提交 cell 与活动尾部拆开；resize/最终化重新建立正确正文 | 遍历组件产出行，未变的 Markdown 可命中缓存，再比较前后行数组 | 原生历史追加，已提交完整条目跳过排版；活动布局和同帧历史投影复用 |
| 终端写入 | 自定义 terminal 生成差分命令，同步更新包住历史与绘制 | 找首末变化行，组装 ANSI 字符串，普通差分一次 `terminal.write`；`2026h/l` 包住更新 | Ratatui cell 差分、连续宽字符 Backend、同步更新均已具备，但 Backend 直接向 `Stdout` 写细碎字符/样式 |

## 选择与实施顺序

1. **减少解析范围。** 在现有 Markdown 缓存内记录源边界及稳定块数，追加正文只解析可变尾部。引用定义与 HTML 等有跨块影响时回退完整解析；宽度变化、内容修订没有有效祖先时按完整正文重建。保留现有解析器和渲染器，不另建一套 Markdown 语法。
2. **共用语义边界。** 先渲染当前正文，历史归档读取同一解析结果记录的边界，避免第二遍专门解析源边界。稳定前缀仍与完整正文的渲染行比较，不能按字符数量猜测可以归档多少行。
3. **减少换行分配。** 字素借用源字符串，构造结果行时才合并为拥有所有权的文本；去掉逐字素 `String` 和一次中间数组。保持中文标点避头、组合字符、emoji、样式和窄窗口行为。
4. **批量终端写入。** 在已有 Backend 外使用标准库 `BufWriter`；保留帧结束显式 flush，查询终端光标前也必须 flush。同步更新保持原有边界，不承诺一次帧只发生一次系统调用。
5. **逐项验收。** 逐字符及不同分片大小下与完整 Markdown 结果比较；真实 PTY 验证历史/缩放/恢复/详情；相同本地 SSE 和相同 debug 构建条件测量流式及输入，出现退化则继续定位。

此轮不移植 Codex 整套动画队列，也不把刷新频率改得更高。Codex 的逐行推进改善视觉节奏，但多一套显示积压和完成收尾状态；pi 的直接合并更新说明它并非流畅的必要条件。先消除计算与写入开销，避免人为等待已经收到的内容。

不采用 pi 的清空 scrollback 重绘，也不采用 Codex 的超长未换行正文省略预览：用户之前明确要求完整正文、原生选择和历史保留。后续若有实际终端证据表明“延迟低但滚动仍跳动”，再单独评估有最大等待时间的按行推进，而不是预先增加配置和调速状态机。

## 正确性边界

- 新块首行尚未收完整时，解析缓存不冻结它之前的块。`|` 等半行内容可能暂时被识别为表格外段落，后续字符又使其成为表格行。归档仍沿用原来的最后顶层块边界并比较渲染行，解析复用与归档游标分别记录，避免改变未换行正文的显示时机。
- 后置引用定义重新计算前文链接；HTML 使用完整解析，因为现有适配器的段落状态可能跨 HTML 事件延续。
- 缓存仍最多 32 份文档、累计 2 MiB 源文本；超出后全量渲染，不删除正文。缓存上限并非所有渲染对象的总内存上限。
- 长单段、开放大表格和引用密集文档仍可能全量处理可变区域；本轮不声称任意长度下恒定耗时。

## 验收结果

上述四项代码改动均已实施。完整 TUI 测试 453 项通过（19 lib、399 TUI、28 PTY、7 Driver），1 项真实上游 smoke 默认忽略；Clippy 全目标零警告，格式及 diff 检查通过。额外重跑 23 项富文本测试通过。测试覆盖每个字符的中间状态、1/7/31 字符分片、100 组块组合、后置引用、HTML、表格、嵌套结构、缩放、最终修订，以及归档边界与原算法的一致性。终端缓冲测试验证相同 ANSI 字节输出，并将一次 40 字符绘制的底层 Write 调用合并为 1 次；这不是实际系统调用计数。

性能使用 macOS ARM64、120×32 PTY、本地 Responses SSE 和 debug 构建。第一轮候选结果相对较早测量有明显波动，因此冻结前后两个二进制，紧邻运行并按场景交换顺序，不以较早的安静时段样本直接推断这轮收益。每场景 400 个片段；均匀发送目标 25ms/片段，突发每 200ms 发送 8 个。下面“前”指上一轮优化完成后的版本，不是最初卡顿版本。

| 场景 | 后 100 段显示延迟中位数，前 → 后 | 全程 P95，前 → 后 |
| --- | ---: | ---: |
| 中文分段正文 | 10.58 → 10.18 ms | 14.19 → 36.49 ms |
| 400 行代码 | 11.44 → 11.37 ms | 14.42 → 16.27 ms |
| 无换行中文长段落 | 15.89 → 14.22 ms | 25.23 → 17.61 ms |
| 突发中文正文 | 36.42 → 34.20 ms | 39.68 → 38.52 ms |

八组均观察到 400/400 个编号。长单段的尾部延迟和 P95 有改善；短正文、普通代码流中位数基本持平，不能宣称所有场景都更快。短正文候选出现最大 229ms 的停顿，P95 反而更差；保留该结果，不删除离群值，也不把原因直接归于网络或其他进程。发送间隔和同机负载有波动，但当前证据不足以隔离该停顿的原因，未证明尾延迟稳定领先。

同样紧邻进行输入对照，每场景 30 个 ASCII 字符：

| 输入场景 | 中位数，前 → 后 |
| --- | ---: |
| 空会话短输入 | 6.73 → 6.77 ms |
| 1,000 字符草稿 | 6.61 → 6.58 ms |
| 8,000 字符草稿 | 10.92 → 10.62 ms |
| 64,000 字符草稿 | 21.77 → 20.96 ms |

本轮输入路径没有明显退化，不把这些小差异解读为普遍提升。首轮独立候选、紧邻 A/B、输入结果与二进制 SHA256 都保存在 [原始汇总 JSON](2026-09-21-tui-refactor-results.json)。采集脚本和逐片时间线位于 `/tmp/golutra-input-diagnosis.iaJxiC/`（`measure.py`、`streaming.py`、`paired_refactor.py`、`paired_input.py`），冻结二进制位于 `/tmp/golutra-tui-ab.GlaqRk/`；临时目录可能被系统清理。对照构建后已恢复并核对候选源码，重新构建当前工作区程序，避免把基线程序留作交付版本。

本轮未实机验证 Windows/Linux、输入法候选窗口或真实终端 GPU 绘制，也没有运行 pi 的性能对照。Codex/pi 表格是源码机制比较，不能作为三者性能排名。之前 Codex 0.155.1 的约 13ms 代码流样本来自不同时间，也不与本轮直接排名。

上一轮的基准保留在 [TUI 延迟验收](2026-09-21-tui-latency.md)，不能把上一轮到更早版本的收益重复算作本轮收益。
