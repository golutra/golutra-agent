# External Verification

## Purpose

Model tool output is useful execution evidence, but it is not always the final
acceptance authority. CI, benchmark harnesses and SDK callers can declare a
trusted command that runs after the model stops and before Runtime chooses the
terminal task state.

```text
model/tool loop
-> candidate workspace
-> caller-declared or command-boundary-discovered external verifier
-> artifact + evidence + objective:test check
-> VerificationRecord
-> StopSuccess / StopFailed / StopPartial
```

In Open mode, a rejected candidate feeds the actual failed command, exit code,
bounded diagnostic output and evidence references back into the same task.
Correction rounds have no default count limit; an explicit task budget,
cancellation or unrecoverable boundary still applies. A passing unit test does
not override a failing external delivery check. No additional model judge is
started for this feedback loop.

## Phase boundaries and delivery order

Review dependent implementation and relevant checks **before** closing a phase
or releasing a resource that the work requires. A normal process wait is only
an observation; it does not make files immutable. File ordering restrictions
come from the actual task, not from the existence of a background command.

Final tests may pass even when an earlier published snapshot is stale or a
required operation happened too late. Projects with such requirements should
check their own delivery evidence in a trusted external verifier, for example
comparing the released snapshot digest with the final source. The runtime does
not infer these business rules from arbitrary prose or model-generated plans.
`completion_criteria` text alone is not an executable semantic assertion.

When a verifier reports a failure, repair only within the task's authority.
Republishing can be valid when the task permits it; a process that was required
to remain alive cannot retroactively be made continuous by restarting it.
Report an unrecoverable ordering failure instead of rewriting evidence or
claiming that a later passing test repairs it. The independent benchmark judge
remains separate from model-visible verification so that feedback cannot
silently change the acceptance standard.

The freshness of observed checks is tracked separately from their success.
Normal source-backed generated bytecode can change without changing the
validated source. The built-in process scanner records all file changes and
only marks derived-only changes when complete before/after snapshots prove
the mapped source stayed unchanged. Runtime consumes that evidence instead
of guessing from the command name. Unknown artifacts, incomplete scans,
failed processes and explicit file edits retain conservative revalidation;
explicit delivery and external verifier assertions are not waived.

`ExternalVerificationSpec` contains `program`, `args`, workspace-relative
`cwd`, `timeout_ms`, `expected_exit_code` and `max_output_bytes`. The process is
argv-based and never interpreted by a shell. The runtime rejects cwd values
outside the workspace and executes with its existing sandbox, cancellation and
network restrictions. Output is redacted and bounded before durable storage.

A passing final verifier may supersede a recovered intermediate tool failure,
while the failed tool event remains in the trace for diagnosis. It never
supersedes failed delivery-path, content, schema, policy or verifier assertions.
Delivery-path checks apply to turns that changed files; a resume turn may verify
an unchanged existing delivery without manufacturing another write.

When a code/workspace task omits the `external_verifiers` field, the command
adapter conservatively examines regular, bounded manifest files at the
workspace root. It discovers one verifier only when exactly one supported
project family is unambiguous: Cargo workspace tests, one meaningful Node
script, pytest for an identifiable Python project, or Go package tests.
Manifest symlinks and oversized files are ignored; mixed or ambiguous roots
produce no implicit verifier and require an explicit list. An explicitly
supplied list remains authoritative; an explicit empty list disables discovery.
Each queued turn owns its own list, so a conversational follow-up never
inherits a previous verifier.

## Entry Points

- `golutra-agent exec`: `--completion-criterion`, `--verify-program`, repeated
  `--verify-arg`, `--verify-cwd`, timeout/exit/output controls. With no explicit
  verifier it uses project discovery; `--no-project-verifier-discovery` opts out.
- App Server and Rust SDK: `AgentTurnOptions.external_verifiers`.
- Python SDK: `Thread.run(..., external_verifiers=[...])`.
- TypeScript SDK: `Thread.run(..., { externalVerifiers: [...] })`.

MCP tools intentionally disable project discovery and do not expose this field
because their arguments may be model-generated rather than trusted operator
configuration.

For bounded repair loops, `scripts/run_agent_benchmark.py` starts an exec turn,
captures its thread id from JSONL, runs the same verifier independently for
bounded failure feedback, and resumes that thread up to `--max-attempts`. The
adapter does not add benchmark-specific behavior to Runtime.

## Trust Boundary

Explicit verifier argv is caller-owned. Discovered commands are selected only
from the fixed project catalog, but they can still execute untrusted workspace
scripts, so CI should run Golutra in an isolated machine or container. Explicit
exec `--approval-mode auto` only resolves model
actions already classified as `Ask`; it cannot approve `Block`/`Deny` actions or
disable workspace, secret, metacharacter, network and sandbox controls.
`exec --yolo` is the separate explicit escape hatch for trusted disposable
environments: it removes those local modification and sandbox controls while
leaving network environment configuration, verifier results and runtime bounds
intact. Since process-only execution has no OS network isolation, use it only
behind an appropriate outer machine or container boundary.
